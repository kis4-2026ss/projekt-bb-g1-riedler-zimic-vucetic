    7     ## 🔍 1. Projekt- & Architektur-Analyse
    8
    9     Das Projekt WishBox besteht aus zwei Hauptkomponenten:

   10     1. Frontend: Eine klassische Single-Page-Applikation (SPA) in Vanilla HTML, CSS und JavaScript (
          src/frontend ). Die Kommunikation erfolgt über die native Browser  fetch  API. Es nutzt einen
          globalen State ( wishlists ,  state ) und führt die DOM-Manipulationen direkt aus.
   11     2. Backend: Ein Node.js Express Server ( src/backend ) mit Sequelize ORM und SQLite-Datenbank (
          db/main.db ).
   12
   13         ┌───────────────────────────┐    ┌──────────────────────────────┐    ┌─────────────────┐
    ⋮         │ Client Browser / Frontend │             │ Express Web Server / Backend │               │ SQLite Database │
    ⋮         └───────────────────────────┘    └──────────────────────────────┘    └─────────────────┘
   21
 22     ### Kritische Geschäftslogik

   23     • Listen-Verwaltung (CRUD): Erstellen, Auslesen, Umbenennen und Löschen von Wunschlisten.
   24     • Wunsch-Verwaltung (CRUD): Hinzufügen, Bearbeiten der Menge/des Titels und Löschen von Wünschen
          innerhalb einer Wunschliste.
   25     • Clientseitige Berechnung & Sortierung:
   26         • Filterung nach Wunschlisten-Titel (case-insensitive).
   27         • Sortierung nach Erstelldatum oder Titel (auf- und absteigend).
   28         • Aggregation von Statistiken (Gesamtanzahl Listen, Gesamtanzahl Wünsche, durchschnittliche
              Wünsche pro Liste, Top 3 Wünsche).

   32     ## ⚠️ 2. Potenzielle Schwachstellen im bestehenden Code
   33
   34     Während der Testabdeckung wurden folgende konzeptionelle und sicherheitsrelevante Schwachstellen
          identifiziert:
   35
   36     1. Fehlende Input-Validierung im Backend:
   37         • Das Backend erstellt Wunschlisten und Wünsche direkt aus dem Request-Body ohne Sanitization
              oder Validierung:  Wishlist.create({ title: req.body.title }) .
>  38         • Risiko: Übergabe von leeren Daten ( null ,  undefined ) ist möglich.
  39         • Modell-Fehler: Das Feld  quantity  im Modell  Wish  wird nicht auf  quantity >= 1  validiert.
              Ein Angreifer kann negative Werte per API einspeisen.
   40     2. Cross-Site Scripting (XSS) Anfälligkeit:
   41         • Die Sanitization erfolgt ausschließlich clientseitig bei der HTML-Erzeugung in  app.js
              mittels  escapeHtml() .
   42         • Risiko: Wenn zukünftige Frontend-Updates oder externe API-Konsumenten vergessen, HTML-Entities
              zu escapen, führt dies zu XSS, da die Rohdaten in der SQLite-Datenbank unbereinigt gespeichert
              werden.
   43     3. Globale CORS-Wildcard:
   44         • Das Express-Backend konfiguriert  cors({ origin: '*' }) .
   45         • Risiko: Dies erlaubt jeder beliebigen Website im Browser, API-Anfragen an das Backend zu
              senden. Für lokale Projekte okay, in Produktionsumgebungen ein kritisches Sicherheitsrisiko
              (Cross-Origin Data Leakage).
   46     4. Fehlende Authentifizierung:
   47         • Es gibt keine Benutzerkontrolle. Jeder anonyme User kann alle Listen und Wünsche löschen oder
              verändern.
   48     5. Datenbank-Deadlocks:
>  49         • Da SQLite dateibasiert arbeitet, sperrt es bei Schreibzugriffen die gesamte Datenbank. Bei
            hoher Concurrency (viele parallele Schreib-Requests) kommt es zu Blockaden.

   53     ## 🛠️ 3. Refactoring-Vorschläge zur Testbarkeits-Optimierung
   54
   55     │ [!WARNING]
   56     │ Das Frontend ( app.js ) ist als monolithisches, globales Skript aufgebaut und greift direkt beim
          │ Laden auf DOM-Elemente ( document.getElementById ) zu. Ein isolierter Unit-Test von z. B.  fmtDate
          │ oder  escapeHtml  ist in Node.js ohne JSDOM-Mocking unmöglich.
   57
   58     ### Empfohlene Refactoring-Schritte
   59
   60     1. Modularisierung des Frontends (Separation of Concerns):
   61         • Extrahiere die reinen Logik- und Hilfsfunktionen in eine separate Datei  src/frontend/utils.js
   62         :
>  63           export function fmtDate(iso) { ... }
 64           export function safeText(s) { ... }
   65           export function escapeHtml(str) { ... }
   66
   67         • Dies erlaubt direkte Unit-Tests dieser reinen Funktionen in Jest mit 100% Ausführungsgarantie,
              ohne DOM-Mocks.
   68     2. Kapselung des API-Clients:
   69         • Lagere API-Aufrufe in ein eigenes Service-Modul ( apiClient.js ) aus. Dies erlaubt einfaches
              Mocken der Netzwerkschnittstelle im UI-Test.
   70     3. Backend-Validierungs-Middleware:
   71         • Nutze Bibliotheken wie  joi  oder  express-validator  im Express-Router, um ungültige Requests
              (z. B. leere Titel oder negative Mengen) bereits auf HTTP-Ebene abzufangen, bevor sie die
              Datenbank berühren.

   75     ## 🎯 4. Teststrategie
   76
   77     Um eine hohe Testabdeckung und Zuverlässigkeit zu garantieren, wurde ein dreistufiger Testansatz
          implementiert:
   78
  80                         /\
   81                        /  \      E2E-Tests (Playwright) - Verifizieren die UI
   82                       / E2E\     und die Integration beider Komponenten.
   83                      /------\
   84                     / Integr \   Integrationstests (Jest & Supertest) - Prüfen
   85                    /  ation   \  Routen, Datenbankzugriffe und Middleware.
   86                   /------------\
   87                  /  Unit-Tests  \  Unit-Tests (Jest) - Testen einzelne Funktionen,
   88                 /________________\ Instanziierungen und Schema-Zuordnungen.
   90
   91     1. Unit-Tests (Datenbank & Modelle):
   92         • Isolation der SQLite-Datenbank im Arbeitsspeicher ( :memory: ).
   93         • Testen der Schema-Generierung, der Tabellen-Verknüpfungen und der Datenbank-Seed-Logik unter
              kontrollierten Bedingungen.
   94     2. Integrationstests (REST API):
   95         • Vollständige Integration von Express und Sequelize.
   96         • HTTP-Requests via  supertest  an die Express-App.
   97         • Abdeckung von Standardfällen (200, 204), Randfällen (leere Payloads) und Fehlerfällen (404 Not
              Found).
>  98     3. End-to-End-Tests (System- & UI-Ebene):
   99         • Playwright steuert einen echten Chromium-Browser.
  100         • Automatischer Server-Start im Test-Kontext über Playwrights  webServer .
  101         • Zustandsfreie E2E-Szenarien, bei denen erzeugte Testdaten am Ende wieder gelöscht werden, um
              Seiteneffekte auszuschließen.
  102     4. Performance-/Load-Tests (Stresstest):
  103         • Programmatische Lasttests mit  autocannon  zur Identifikation von Performance-Flaschenhälsen
              (Durchsatz & Latenz).

  139     ## 🚀 6. Ausführen der Tests
  140
  141     │ [!NOTE]
  142     │ Alle Befehle müssen im Verzeichnis  src/backend  ausgeführt werden.
  143
  145       cd src/backend
  147
  148     ### 1. Unit & Integration Tests (Jest & Supertest)

> 149     Startet Jest und führt alle 25 Backend-Tests aus (E2E-Tests werden ignoriert):
  151       npm test
  153
  154     ### 2. End-to-End Tests (Playwright)

  155     Startet den Test-Server im Hintergrund und führt die 5 E2E-Szenarien im headless Chromium-Browser
          aus:
  156
  157       npm run test:e2e
  159
  160     ### 3. Lasttests (Autocannon)

  161     Startet eine eigene Express-Instanz im Arbeitsspeicher auf Port 3001 und führt 5 Sekunden lang einen
          API-Stresstest durch:
  162
  163       npm run test:load
